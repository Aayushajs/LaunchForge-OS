Teams and security

Isolation and security

How workspaces are kept apart on a shared server, and how secrets, webhooks and accounts are protected.

Workspace isolation#

Several teams can share one installation. Workspaces cannot see each other's resources, take each other's domains, mount the host or exceed their quotas. Only the platform workspace can administer the server itself.

Risk Control
Reaching another workspace's databases over the network Each workspace has its own overlay network; only Traefik joins them all
Changing Traefik, Docker or the server Host administration is limited to the platform workspace
Escaping a container through mounts The Docker socket, /, /etc, /var/lib/docker and similar paths cannot be mounted; privileged containers and host namespaces are rejected
Taking someone's domain A hostname belongs to the first workspace that adds it
Using all the memory or CPU Quotas are checked on every deploy; services without limits get the default limits
Forged Git webhooks Signatures are verified against the raw request body
Reading someone's secrets Environment variables and credentials are encrypted at rest; every API call checks ownership

The full list, with the tests that prove each control, is in the threat model.

Platform and tenant workspaces#

Workspace Who Can do
Platform workspace The first one, created with the owner account Everything, including the server itself: Traefik, Docker, Swarm, web server settings, updates, and the quotas of other workspaces
Tenant workspace Every other workspace Deploy apps and databases inside its quota, invite its own team, connect its own Git accounts and servers. Cannot see or change the server or other workspaces.

Pages that manage the server itself (Web Server, Traefik, Docker, Swarm, Requests and host Monitoring) are hidden from tenant workspaces and refused by the API if called directly.

Workload policy#

Every service is checked before it is deployed: no privileged containers, no host network or PID namespaces, no devices, no dangerous capabilities, and no mounts of the Docker socket or system paths. The full rule list is in Docker Compose and templates.

Networks#

Every workspace has its own private network. Inside a workspace, you can create extra overlay networks under a service's Advanced → Networks and attach services to them, for example to keep a database reachable from one app only.

WORKSPACE_NETWORK_ISOLATION=false puts every service back on one shared network; use it on single-owner installations only.

Encryption at rest#

Secrets are encrypted at rest with AES-256-GCM: environment variables, database passwords, SSH keys, Git tokens, registry and S3 keys, and certificate keys. The encryption key is a Docker secret created by the installer; keep it with your backups.

Webhooks#

Git webhooks and deploy webhooks are verified by signature, and deliveries with a wrong signature are rejected with 401. See API and webhooks.

Accounts#

New passwords need at least 12 characters, and sign-in, sign-up, password reset and two-factor checks are rate-limited per address. Two-factor authentication and passkeys are under Settings → Profile. See Sign-in and email.

Reporting a vulnerability#

Please report security issues privately as described in SECURITY.md.
